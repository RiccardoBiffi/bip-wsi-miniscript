# Hardware-wallet harness contract

The manifest defines the cases, scenarios, fixtures, steps, assertions and evidence required for the draft. The runner repository is the implementation target for device connections, execution and evidence collection. The local tools validate the specification, fixtures and execution reports. [CTS manifest](../cts/manifest.json) · [Runner repository](https://github.com/RiccardoBiffi/wsi-miniscript-runner)

## Inputs and scope

Load the manifest and its referenced artifacts from one checkout. Validate the manifest against its schema and verify every declared artifact digest. Record the SHA-256 of the exact manifest file bytes and the checkout revision. Resolve fixture IDs using the fixture catalogs. Preserve the bytes of frozen fixtures. A scenario that supplies runtime values, such as a registration handle or a regtest funding outpoint, uses the same transformations and assertions as the fixture defines and records the exact instantiated values in its evidence. [Manifest schema](../cts/manifest.schema.json) · [WSI fixtures](../cts/fixtures/wsi.json) · [Bitcoin fixtures](../cts/fixtures/bitcoin.json)

Start a report for one endpoint mode, signer model and firmware, adapter revision, carrier binding, configuration and Bitcoin network. Discover the endpoint with `capabilities`, record the original response, and select the profiles and claims under assessment. Repeat the assessment for each physical carrier binding and network included in the stated scope. One binding can carry a file or byte stream over USB, serial, removable media or QR as specified by its implementation.

Use a dedicated test device or simulator provisioned with the suite's public test key material. Record the fixture key-context ID and how it was activated. For an address-prefix or network-binding check on an advertised public network, derive and inspect the synthetic fixture only. Use a private regtest chain for on-chain funding, maturity and script execution. Run each stateful scenario in an isolated session or reset the affected test state to its declared baseline before setup.

## Scenario execution

1. Compute the required scenarios from the Core baseline, profile expansion, feature prerequisites and axes in the manifest. For each scenario, enumerate the applicable parameter tuples. Each tuple becomes its own report row. Expand the combinations that the protocol permits for a signature family, policy format, PSBT version, transaction version and registration mode. For a probe of an unadvertised value, use the manifest's deterministic cases and record the value used. A scenario conditional on a stored or token handle applies when that mode is claimed. Per-operation registration has its own fresh-approval checks.
2. Resolve fixture operands and create fresh unpredictable IDs for new live requests. Preserve the request ID and complete bytes for intentional identical retries or conflict probes. Record the selected transport, test setup, exact request and response bytes, and the ordered actions and observations. Record a local import failure, transport close or timeout at its actual boundary. A semantic WSI error has the response correlation fields and the expected error code.
3. Execute the scenario against the declared boundary. Check host responsibilities such as envelope correlation and signature merge at the host interface. Check signer responsibilities such as ownership, supported policy validation and exact signature scope at the device boundary. When an adapter translates WSI to a native request, capture both sides where the binding permits it or use an independently inspectable firmware path. Attribute device enforcement to evidenced device behavior.
4. Evaluate all assertions for the same parameter tuple and gather the evidence kinds specified by the scenario. Compare deterministic values directly. Treat valid signatures as cryptographic results that may vary across runs. Capture trusted-device review and approval or refusal as timed observations tied to the request and step. Use a physical device interface for a hardware UI assertion.
5. Emit the ordered results in the report format. Record a failure for an unmet assertion with attributable execution evidence. Mark a required scenario `not-run` if setup, evidence or an independently checkable oracle is unavailable. Record a reason with each `not-run` or `inapplicable` entry. Applicability comes from the manifest and scope. [Report schema](../cts/report.schema.json)

The manifest distinguishes frozen byte-level data, generated parameter and boundary cases, and actor steps for actions such as confirming on a device or advancing a chain. For each resource under assessment, take the maximum requirement of the applicable mandatory positive fixtures and apply the 4,096-byte container minimum. A declared limit below the corresponding minimum fails the claim. Cover a valid attainable boundary at or below each declared limit and an over-limit input. Respect the protocol ceiling and context-specific validity constraints when selecting the tested value. Record the resource, measured value, claimed limit and observed outcome. Capture allocation or bounded parser evidence if a scenario asserts rejection before allocation.

## Independent checks

- For envelope and carrier tests, independently recompute canonical encoding, request correlation, policy identity and framing. Check stream reassembly at the dispatch boundary. An incomplete container must leave the operation unexecuted. For a complete retry after a disconnect or restart, observe whether the original complete response is recovered or fresh approval is requested, as allowed by the draft.
- For policies and addresses, derive the keys and complete scripts at the exact branch and index. Compare origin, network, `policy_id`, address and `script_pubkey`. For Taproot also compare the instantiated internal key, leaf and branch hashes, Merkle root, output key tweak and control block whenever the case uses them. Record the independent descriptor and script tool versions or revisions.
- For signing, decode the original PSBT in its native version and derive its effective unsigned transaction. Recompute the digest independently for the requested inputs, exact keys, modes, leaf hashes and sighashes. Check every update against its allowed PSBT key encoding, original target and verified signature. Merge only after all checks succeed. Verify PSBT preservation from the original map entries. For v2, use a v2-aware parser and preserve locktime and modifiability semantics when projecting an unsigned transaction for another verifier.
- For fees and change, authenticate each required prevout from its full previous transaction and output index, compute values in satoshis, and compare the exact wallet and derived script behind each change claim. Collect the trusted display's actual destinations, amounts, affected policy identities and verified or unverified fee status. For multi-account signing, inspect all outputs.
- For satisfaction, use an independent script implementation and isolated Bitcoin Core regtest. Record the node revision, funding transaction and block, relevant median time or height, final witness and acceptance result. Check signing eligibility against transaction fields and chain maturity against the controlled chain. A correct signature can precede maturity. Exercise the case's expected valid or invalid witness and the configured maturity boundaries. Pin or probe the oracle's supported PSBT versions before using its RPCs to interpret a PSBT.
- For registration and interruption, preserve the sequence of device approvals, rejections, request and response transport events. A lost response leaves the host completion state unknown. Reuse the exact approved payload where a case expects a retry, and record every approval required by the device after re-establishing the session.

When a scenario concerns a fact internal to opaque firmware, gather direct implementation evidence or state the observable limits in the result. Examples include whether the device released a signature before transport interruption, whether a scope filter was applied inside the signer, and whether decoding refused a size before allocating its backing buffer.

## Evidence contract

Each report row identifies the original case, the scenario and its parameter tuple. Each referenced evidence item has a unique ID, kind, package-relative file path and SHA-256 of the distributed bytes. A single evidence file can support multiple rows when it identifies each covered observation.

| Kind | Evidence |
| --- | --- |
| `wire` | Captured request, response and carrier events at a named boundary, including any local error and observed timing. |
| `oracle` | Independent derivation, cryptographic verification, parser or regtest output with its inputs and tool revision. |
| `device-ui` | Screen capture or signed observation of the device's trusted interface, tied to request, step, displayed facts and operator decision. |
| `device-path` | A correlated device-side trace or inspectable firmware path for the tested build, identifying where the enforcement occurred. |
| `process` | Provisioning, isolation, release or rerun evidence, including fixture and key context identifiers. |

Place the evidence files alongside the report or below its directory. Keep original captures in the controlled assessment environment and include public or redacted copies as the publication policy permits. Document any redaction and preserve enough evidence to reproduce each verdict. Record the hash of the evidence copy referenced by the report. Protect any secret or sensitive data encountered during an assessment.

## Repository checks

Run `python3 tools/cts.py verify` to validate the committed CTS and fixtures. Run `python3 tools/cts.py verify-regtest` to exercise the independent regtest checks. Run `python3 tools/cts.py generate` when changing generated fixtures, then verify the resulting artifacts and review their diff. Validate an execution package with `python3 tools/cts.py verify-report REPORT`. See the [conformance guide](conformance.md) for the assessment procedure and decision rule.

## Manifest interpretation

Each value in `requires` is a conjunction of named conditions. A scenario applies when at least one conjunction is true. An empty conjunction is always true. Derive the `profile:`, `feature:`, `context:`, `registration_mode:`, `psbt_version:`, `mode:`, `carrier:` and `binding:` conditions from the assessment scope. `binding:` uses the binding medium. Descriptor-pair format support activates descriptor-pair cases. A full context declaration activates that context's full corpus. Use `axes` to expand the selected scope into explicit tuples, including separate ECDSA and Schnorr dimensions.

Resolve `catalog:path.to.record` against a manifest artifact. Dollar-prefixed values name a tuple axis, the scoped `network`, the lowest advertised `preferred_psbt`, or the value saved by an earlier exchange in the same scenario. An outcome assertion refers to the operation under test. When a scenario has a positive control and a later negative probe, apply success assertions to the control and the terminal or no-effect assertion to the probe. Compare deterministic expectations against the same fixture instance used for the request.

- `exchange` runs the named WSI method. Use the referenced policy's BIP-388 record unless the step selects a descriptor-pair. Use the explicit network, label, address position and registration handle from the step or its setup. Default label is `WSI CTS` and the default address position is receive branch zero at index zero. Materialize key-context switches, registration modes and approval choices as harness actions. Serialize only fields allowed by the corresponding WSI record.
- For `sign_psbt`, construct the canonical fixture using the selected policy IDs, amounts, PSBT and transaction versions, optional external input, and the requested condition or leaf. If unspecified, use transaction version 2, the lowest advertised PSBT version, the fixture's supported default sighash and `verified-prevouts`. Obtain or verify the registration for each targeted account. Populate `input_bindings` for targeted inputs and derive `change_bindings` from separately specified claims. The TX-008 destinations `external`, `other-account` and `same-seed-other-policy` resolve to `external-wpkh`, `wsh-sortedmulti` and `wpkh-account-1` respectively at branch one, index zero. Preserve the original PSBT bytes and sign target set until the response has been checked. Select leaves by the fixture's `tap_leaf_order`. Each mutation transforms a copy of the relevant fixture at its declared boundary. [Bitcoin fixture constructor](../tools/bitcoin_fixtures.py) · [Mutation recipes](../cts/mutations.json)
- `wire` delivers the exact fixture bytes for the chosen carrier and direction. `device` records a provisioning, state or review action. `carrier` controls a named delivery or interruption event and records the dispatched request count. Use the binding's actual segmentation for a QR test.
- `oracle` performs the independent check described by the action and the ordered case assertions. For a safe corpus, exercise every applicable positive fixture within the mandatory context scope. For an invalid-policy scenario, select the negative entries named in `entries`. Use the catalog's exact address/script expectations and verify any required assembled witness. For subset claims, positive probes are scoped to the declared support and excluded features get refusal or unknown checks. For version and sighash probes, subtract the advertised values from the specified candidates and test each remaining value.
- `assessment` evidences a process or capability obligation, such as the treatment of a previous report after a configuration change. Record the old and new scope values and the resulting decision or repeated test set.
